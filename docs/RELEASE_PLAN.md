# リリースまでの実行計画

策定日: 2026-10-08  
対象: 読書管理 Web MVP の一般公開

## この計画の位置づけ

設計・MVPスコープの正本は `../../book-manager-web-mvp-plan.md`（v2、2026-09-12）。この文書は、策定時点のコード・GitHub Issue・PRを踏まえて、残作業の優先順位・依存関係・公開条件をまとめた実行計画である。

ホスティングは最新の [#15](https://github.com/haino357/book_manager_web/issues/15) と [Cloudflare調査](CLOUDFLARE.md) に従い、**Cloudflare Workers + OpenNext** を前提とする。DB・認証は **Supabase** を使う。正本・README・[デプロイ手順](DEPLOY.md) に残るVercel前提の記載は、公開準備で整合させる。

以下の実装・CIの状態は策定時点の確認結果であり、実DB・ブラウザ・本番での確認完了を意味しない。完了した作業と未検証項目は、各IssueとPRに根拠を残す。

## 進め方と工数

**品質の修正 → MVPの残機能 → 本番環境 → 限定公開 → 一般公開** の順に進める。ただし、Cloudflareでの動作とモバイルJSON仕様は最初に確認し、ドメイン・メール等の準備は機能開発と並行して進める。

工数は1人で作業する場合の概算。契約・メール設定・モバイル側の対応待ちは別枠とし、工程1の結果で見直す。暦上の公開日はまだ確定しない。

| 工程 | 作業 | 完了条件 | 目安 |
|---|---|---|---|
| 1. 公開上の不確実性を解消 | PR #61の実DB確認、OpenNextの動作検証、モバイルJSON仕様の確認 | 保存の整合性、Workers上の認証・更新・Sentry、インポート仕様について実装方針を判断できる | 2〜3人日 |
| 2. データと基本操作を安定化 | #49・#53・#48・#46・#50・#55 | 障害を正常な0件と表示せず、データ・集計が欠落せず、誤登録を取り消せる | 4〜6人日 |
| 3. MVP機能を完成 | #8 メモ、#10 インポート、#58 案内・資料の更新 | メモの追加・編集・削除と実際のモバイルデータの取り込みができる | 4〜7人日 |
| 4. 本番環境を完成 | #15 Workers、#38 DB・バックアップ、#35 認証、#4 問い合わせ先 | 本番URLで第三者が登録・利用・退会でき、障害時の復旧手順がある | 3〜5人日 |
| 5. 公開判定 | #18 RLS、#17 Lighthouse、主要操作の通し確認、少人数での利用 | 公開条件を満たし、重大な不具合が残っていない | 2〜4人日＋観察期間 |

**合計15〜25人日程度＋限定公開の観察期間3〜7日**を仮置きする。観察期間が過ぎただけでは公開せず、公開条件と不具合の状況で判断する。

### DB変更と公開の順序

現行のデプロイ資料には、マージ後のDB適用と自動デプロイの順序が曖昧な部分がある。新しいDB構造を使うアプリが先に公開されないよう、次を手順に組み込む。

1. DB変更の後方互換性とバックアップを確認する。
2. 自動デプロイの開始条件を制御し、DB適用・確認より先に新コードが公開されないようにする。
3. 互換性のある追加変更を適用し、マイグレーション履歴を確認する。
4. 対応するアプリを公開し、主要操作を確認する。
5. 削除・名前変更等の破壊的変更は別段階に分ける。障害時にアプリだけ戻せる条件と、DB復元が必要な条件を明記する。

## 工程5: 公開条件と限定公開

### 一般公開の必須条件

- [ ] `npm run typecheck`、`npm run lint`、`npm test`、`npm run build`、導入したOpenNextのビルドが成功する。
- [ ] 本番で登録、メール確認、Googleログイン、パスワード再設定、ログアウト、退会を確認する。
- [ ] [#18](https://github.com/haino357/book_manager_web/issues/18): 他人の蔵書・メモ・履歴を画面・直接API・RPCから読み書きできない。共有書誌やプロフィールの権限も確認する。
- [ ] PC・スマートフォンで、登録→読了→再読→メモ→評価→統計→削除を通して確認する。
- [ ] 999／1,000／1,001冊、読了日不明、再試行・同時更新、外部検索先の障害で、データ・集計・表示が破綻しない。
- [ ] インポート後の冊数・メモ数・履歴数が一致し、再投入で意図しない重複が生じない。
- [ ] Sentry通知、バックアップの取得と復元、アプリの切り戻しを確認する。
- [ ] 公開ページ・連絡先・機能紹介が実態と一致する。
- [ ] [#17](https://github.com/haino357/book_manager_web/issues/17): Lighthouseの対象指標が80以上。認証必須ページのSEOは公開ページと分けて評価し、対象と結果を記録する。

### 限定公開から一般公開へ

少人数で3〜7日利用し、登録・検索・保存・認証の不具合とSentryの通知を確認する。データ欠落、権限逸脱、主要操作の失敗が残る場合は一般公開を延期する。修正後は影響範囲を再確認し、結果を記録して公開を判断する。

ローカル確認用アカウントは `@example.test` を使い、確認後は設定画面から退会する。本番のメール到達確認には実際に受信できる承認済みのアドレスが必要なので、専用の検証方法を用意する。画面や本番で確認できなかった項目は、理由付きで未確認のまま残す。

公開後は主要操作・認証メール・エラー通知を再確認する。モバイル側の #37／#40 への公開URLの記載も、依頼されたタイミングで行う。
